## 改动与取舍

`TcpClient` 增加 `controlTimeoutMs`，默认保持 5000 毫秒，合法范围 1..2147483647 的整数，构造后只读，避免期限被修改成无效值后出现未注册 waiter 却写出命令。它约束 CONNECT 和 receipt；普通 `waitFor`/`Subscription.next` 超时保持会话存活。控制等待失败仍关闭会话、清理等待者/缓存/定时器；不加入重连或重发策略。

receipt 失败增加 `operation`（SEND/COMMIT 等）、`receiptId`、`outcomeUnknown`、`cause`。只有本次请求开始调用 `socket.write` 后才标为结果未知；核心验证或本地写缓冲限制在写调用前拒绝时为 false。非法 command 在注册等待前拒绝，错误不保留原始 command 对象或任意字符串。普通观察超时为 `STOMP_EVENT_TIMEOUT`，receipt 超时为 `STOMP_RECEIPT_TIMEOUT`，握手超时为 `STOMP_CONNECT_TIMEOUT`。EOF 分为 `STOMP_PEER_EOF` 与 `STOMP_TRUNCATED_STREAM`，本地关闭为 `STOMP_CONNECTION_CLOSED`。Node I/O 的 code 和原始异常保留在 cause 中，broker ERROR 的 frame/reason 也保留；其原有错误 name 保留，避免破坏按错误类型判断的调用方。CLI 显示 receipt ID 时用 JSON 引号转义，明确要求对账后再重试。既有 reliable-send demo 改用公开的 receipt API 和 `controlTimeoutMs: 400`，实际断言超时后关闭；不再用底层 send + 观察等待绕开控制超时行为。前一交付轮未运行该 SDK 依赖 demo；本轮续验已通过其真实 bridge 运行和 golden 比对。

`outcomeUnknown` 是保守的客户端知识边界，不是“broker 一定执行了”或“broker 一定回滚了”。若 COMMIT 已送到 broker 而 RECEIPT 丢失，客户端不能自动 ABORT 或重发来消除歧义。`Transaction.state === 'failed'` 仍表示客户端未获得成功确认。应用需要稳定业务 ID、查询/对账或自身幂等约束；STOMP receipt 不确认消费端业务完成。本次不改变核心的事务 ACK staging/ABORT 行为，也不把 broker 特定 ACK 回滚差异概括成通用承诺。

Classic runner 的 `--tls` 生成两天有效的自签 localhost 测试证书，唯一 connector 为 `stomp+ssl://127.0.0.1:PORT`；测试客户端显式信任该公证书并校验主机名。仍使用无持久化、无 JMX/Web 的临时 profile，测试账号不是真实用户凭据。关闭进程后删除 PKCS12 私钥，保留配置摘要、公证书及测试日志。结束后检查端口释放；不会停止已有端口占用者。

新增认证/TLS 负控制与三版本测试包含：错误 CA 和错误主机名不调用 CONNECT；匿名与错误口令拒绝；可信 TLS/正确认证；含 NUL/255 的二进制收发；版本化 ACK；事务 SEND 在 COMMIT 前的 100ms 有界不送达观察、COMMIT 后送达、ABORT 后 250ms 不送达观察，以及后继非事务消息正控制。有限时间的负观察不能证明无限时间不投递。NACK 只记录发送，不声称重投递。事务 ACK 回滚、mTLS、生产证书、生产网络未验证。

runner 校验 JSON 中认证负控制、TLS 模式、三个实际协商版本和事务明细；单个 `status: PASSED` 不足以判定成功。此验证守卫避免残缺日志或错误 profile 被误标为完整通过。

## 三分钟真实演示与交付

目标是让用户能解释一个实际问题：**消息可能已经到 broker，但发送方没有收到确认；这时盲目重发可能产生重复业务。** 本演示用真实 Classic broker 跑一个 STOMP 1.2 场景，不重跑已有三版本矩阵，也不增加产品 API。

准备条件：从源码根目录运行；已有 Node 24、Python 3、Java/keytool、lsof、官方 SHA512 已核验的 Classic 6.3.2 解压目录；先用可用 SDK 执行 `moon build --target js`，生成 `_build/js/debug/build/bridge/bridge.js`。运行前准备依赖的时间不计入演示。脚本不下载、不自动安装；缺 bridge 会在启动 broker 前失败。`--output` 必须是源码树外的新目录，端口须无现存监听。

准备好后只需一条命令（替换本机路径）：

```sh
python3 scripts/classic-run.py --home /path/to/apache-activemq-6.3.2 \
  --java-home /path/to/jdk --output ../moonstomp-demo-evidence \
  --port 62616 --tls --demo
```

`--demo` 必须带 `--tls`，只执行 `examples/classic-three-minute.cjs`；不执行三版本矩阵。broker、测试证书、故障中继由这一命令创建和清理。正常路径实测全程 **3933ms**，退出 0；终端保留以下六行断言摘要：

```text
tls-authentication: TLS certificate and hostname checked; wrong credentials rejected; authenticated session active.
transactions: COMMIT delivered confirmed-order; ABORT did not deliver cancelled-order; pre-COMMIT read stayed empty (100 ms).
unknown-no-replay: Observer received one order; relay dropped its real broker RECEIPT; sender timed out with unknown outcome, closed, and forwarded no resend.
cleanup: broker port closed=True; temporary private key removed=True
Wasm GC compatibility remains FAILED; this focused demo is not full acceptance.
RESULT PASSED; elapsed_ms=<本次实际毫秒数>
```

三分钟讲解顺序：

| 时间 | 现场看什么、怎么解释 |
|---|---|
| 0:00–0:40 | 执行命令。TLS 校验证书/主机名，STOMP 认证拒绝错口令；这两层分别回答“连到谁”和“谁能使用 broker”。公开输出没有账号或口令。 |
| 0:40–1:25 | `cancelled-order` 先 ABORT，随后 COMMIT 的 `confirmed-order` 被观察方接收；COMMIT 前 100ms 没有可见消息，之后 150ms 没有额外消息。说明这只是当前 profile 的有界观察，不是跨系统事务或消费业务完成保证。 |
| 1:25–2:30 | 中继把一条真实 SEND 发到 broker，直连观察方确实收到了订单；中继只丢弃它的真实 RECEIPT，发生在发送方 MoonBit decoder 之前。发送方在 600ms 控制期限后得到 `STOMP_RECEIPT_TIMEOUT`、`outcomeUnknown:true` 并关闭。结果里 `acceptedConnections=1`、`forwardedSends=1`、`droppedReceipts=1`，后续发送被本地拒绝；应用应先对账或依靠业务幂等 ID，而不是直接重发。 |
| 2:30–3:00 | 展示清理和限制。MoonBit 承担帧解析、receipt/事务状态，Node 只做 TLS/I/O；演示中继用当前 MoonBit parser 检查完整帧。Wasm GC 仍有独立最小复现失败；本演示成功不等于全量验收，更不承诺获奖。 |

故障注入是可见的测试设施：broker 只监听 `127.0.0.1:62616`，中继另开一个自动分配的回环端口；中继两侧都走校验证书的 TLS，用临时测试 PKCS12，不关闭 `rejectUnauthorized`。它只丢弃指定 receipt ID 的一帧，记录转发次数；不是自造 broker，也不是在适配器内部伪造超时。`examples/receipt-loss-relay.cjs` 只服务本演示，限制缓冲 1 MiB、单 socket 空闲 3 秒，不作为生产代理。600ms 只覆盖这个演示发送方的控制期限，库默认 5000ms 不变。

清理和失败可见性：客户端在 finally 中 stop；中继销毁前后端 sockets 并关闭监听；runner 只终止自己创建的 broker，删除临时私钥并检查端口释放。每个演示子命令最多 20 秒，整体超过三分钟会标失败。已有监听时拒绝，不杀进程；单 socket `SO_REUSEADDR` 仅避免本次排练的 TIME_WAIT，不改系统设置，也没有 `SO_REUSEPORT`。

已经聚焦验证两条失败路径：中继建立前的测试密钥读取失败、建立后的上游 TLS 断开，均退出 1；broker/端口/私钥清理成功，后者中继剩余 sockets=0。测试通过进程局部 Node preload 注入错误，未向产品增加故障开关。公开 stdout/stderr 和子演示 JSON 都没有固定测试口令或注入的敏感标记；不打印原始 broker ERROR、cause 或任意消息体。私有配置和 broker 调试日志仍可能含固定的合成测试用户名/口令，不是脱敏后的生产日志；本脚本不接受真实用户凭据。

完整断言、耗时及失败日志保存在 `classic.json`、`classic-three-minute.stdout.txt` 等文件。4 项中继分帧边界测试和 9 项 profile/演示证据守卫通过；它们不替代这次真实演示。未重跑此前已通过的完整 broker 矩阵。无需 SDK 的 `node examples/error-context.cjs` 仍只是模拟错误展示，可离线讲解，不能作为真实 broker 回执。
